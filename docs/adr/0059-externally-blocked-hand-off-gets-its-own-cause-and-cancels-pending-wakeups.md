# Externally-blocked hand-offs get their own Hand-Off Cause and cancel pending wake-ups, not a new blocked-reason or an inferred state

Issue #367, found during the gmail-labeler workspace retrospective (2026-10-26): a Task's Run can determine that its only remaining blocker is something only the user can clear (e.g. an OAuth consent flow plus a credentials file). Today that lands as an ordinary `agent_requested` Handed-Off Run, indistinguishable from any other "agent asked to stop." Nothing on the board/Task Drawer tells this apart from a hand-off that just needs review, and nothing stops the owning Workspace's chained `schedule_wakeup` check-ins from spawning fresh Tasks against the same dead end on every wake, for days.

Decided: add a third Hand-Off Cause, `awaiting_user_action` (Externally-Blocked Hand-Off, GLOSSARY.md), produced only by a new tool — a sibling to `hand_off_task`, following ADR-0054's precedent of an explicit tool and an explicit value rather than inferring the case from free text or a retry count. Unlike `hand_off_task`'s existing nudge-once gate (requires a prior `ask_user` interrupt in the same Run), this tool needs no such gate: an externally-blocked scenario isn't one `ask_user` could resolve anyway. It's written to `task_queue.handoff_reason` (the column ADR-0056 already established and already surfaced through `BoardContext.handoff`) rather than `tasks.blocked_reason` — that column is never set on the hand-off path today (hand-off settles `tasks.status` to `blocked` with no `blocked_reason` at all, per ADR-0054), so extending it would mean populating a field nothing else on this path uses, instead of the one that already does. Declaring an Externally-Blocked Hand-Off also resolves the owning Task's `workspaceId` to its Workspace's `threadId` and cancels any wake-up still pending there — a thread holds at most one pending wake-up at a time (a DB unique index), so the lookup is `WakeupStore.getPending(threadId)`, not a filtered list — by calling `WakeupRegistry.cancel(wakeupId, source)`, not `WakeupStore.cancel()` directly: the registry also clears the in-process timer backing the wake-up, the same way the existing `cancel_wakeup` tool does. Removing the thing that would trigger another check-in at all, rather than trusting every future wake-up turn to notice the Task is still blocked and hold back on creating more. `board-rules.ts`'s drag-to-queue gating is extended to reject a bare drag-to-queue on an `awaiting_user_action` Task unconditionally (no scope check, unlike `exhaustion_cap` — this cause was never about repeated identical-scope attempts), forcing the existing Hand-Off Guidance flow (ADR-0057) as the one way out. Hand-Off Guidance itself needs no change: it already applies to any Hand-Off Cause.

Explicitly not touched: Narrowed-Retry/Exhaustion-Cap (ADR-0056) and cron catch-up/recurrence. Both were suspected as the actual runaway-generation mechanism going in, but ruled out on inspection: Exhaustion Cap already caps at exactly one Narrowed Retry per Exhaustion Streak before escalating, and `store.fireCronTask()`'s existing gate (requires `tasks.status === 'scheduled'`) already excludes firing a `blocked` Task. Neither needed new suppression logic; the actual vector was the Workspace-chat-thread wake-up chain, a mechanism neither of them touches.

Also explicitly out of scope: automatically detecting that the blocker has cleared (a file appearing, a webhook firing) and auto-resuming the Task. Clearing an Externally-Blocked Hand-Off is an explicit user action only — Hand-Off Guidance, or any other existing resume path — same as every other Hand-Off Cause; no incidental Workspace-chat message or external event resumes it on its own. Building generic event-driven resume is real infrastructure in its own right and is tracked separately.

## Considered Options

- Add a new `tasks.blocked_reason` value instead of a new `handoff_reason` value — rejected: `blocked_reason` is never populated on the hand-off path today (only on the dependency-failure and awaiting-children paths); reusing `handoff_reason`, which the hand-off path already writes and which the board already reads via `BoardContext.handoff`, needed no new plumbing.
- Add a `cause` parameter to the existing `hand_off_task` tool instead of a new tool — rejected: the two cases need genuinely different side effects (cancelling a Workspace's pending wake-up is specific to this one), and a single tool whose behavior branches per enum value is exactly the kind of generic, configuration-driven tool this project's composition-over-customization principle warns against; ADR-0054 already set the precedent of a new tool per new case instead.
- Infer "externally blocked" from a pattern — e.g. N consecutive `agent_requested` hand-offs on the same Task with no forward progress — rejected: the same reasoning ADR-0054 already rejected inference for applies here; an explicit, agent-declared signal is auditable and intentional, a heuristic threshold would eventually be wrong.
- Leave any pending wake-up alone and instead inject "this goal is externally blocked, don't create tasks or re-schedule" context into future wake-up turns — rejected: relies on every future turn correctly noticing and honoring a soft instruction, which is the same class of failure that produced this bug in the first place. Cancelling the wake-up makes the suppression structural instead of prompt-dependent.
- Gate the drag-to-queue rejection on unchanged scope, mirroring `exhaustion_cap` — rejected: `exhaustion_cap` exists specifically to stop repeated identical-scope retries; an externally-blocked Task isn't about scope at all, so an unconditional rejection (until Hand-Off Guidance is provided) is the only check that actually matches what's being guarded against.
