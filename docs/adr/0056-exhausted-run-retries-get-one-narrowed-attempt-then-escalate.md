# Exhausted-run retries get exactly one narrowed attempt before escalating to a system-caused hand-off

Issue #369: a Run that fails by hitting a hard resource limit — the step/recursion limit (`GraphRecursionError`) or, once Turn Overflow truncation still doesn't fit, the trim budget (`ContextBudgetExceededError`) — an **Exhausted Run** (GLOSSARY.md) — currently retries (via cron re-fire or a human dragging it back to `queue`) with identical scope and no memory of what the prior attempt already tried, and tends to fail the same way again at even higher cost. Today only a free-text `summary` records why a Run failed, with no way to reliably tell an Exhausted Run apart from a Stalled Run or a genuine crash.

Decided: add a structured `failure_reason` (`'out_of_steps' | 'turn_overflow' | 'other'`) to the run row, written at the existing failure branches in `task-execution.ts`. A Task may retry with unchanged scope (its Scope Snapshot's title/description, exact and whitespace-normalized) exactly once per Exhaustion Streak — that one Narrowed Retry gets a condensed summary of what the prior attempt already tried/ruled out (a new, dedicated one-shot LLM summarizer, injected additively alongside the existing one-line summary and Handoff Notes in `buildRunKickoff()`) plus an explicit statement that a second Exhausted Run will escalate. If that Narrowed Retry also ends as an Exhausted Run with unchanged scope, the run settles to the existing `handed_off` status / `blocked` Task bucket (reusing ADR-0054's machinery) with a new Hand-Off Cause, `exhaustion_cap` — the first time `handed_off` is produced by anything other than the agent calling `hand_off_task`. A cron-scheduled Task currently `handed_off` for any cause is skipped on its next fire rather than re-enqueued; a drag back to `queue` is rejected outright specifically when the cause is `exhaustion_cap` and scope is still unchanged (not for `agent_requested` hand-offs, which were never about repeated identical scope).

Scope: this applies only to Tasks that appear on the board. A Sub-Agent Task's analogous step-exhaustion is already reported back to its parent via the loop guard's `escalationMode: 'throw'` (`StagnationLimitError`), never via this mechanism; a Sub-Agent Task's Turn Overflow can still throw `ContextBudgetExceededError` same as any Run, but since Sub-Agent Tasks never reach the board or the Task Drawer, the Exhaustion Streak/Cap/Narrowed Retry machinery here has nothing to act on for them either way.

## Considered Options

- Require the Task be split into child sub-tasks (via `create_tasks`) before any retry is allowed, instead of carrying forward a condensed summary — rejected: needs new decomposition infrastructure the issue doesn't clearly justify yet; condensed-summary carry-forward reuses an existing precedent (`workspace-summarizer.ts`) at a fraction of the cost.
- A separate narrowing strategy per failure type (step-limit vs. turn-overflow) — rejected: no evidence yet that the two need different treatment; one unified mechanism for both, revisit if data says otherwise.
- Make the one-retry cap configurable, alongside `recursionLimit`/`subAgentRecursionLimit` in `AgentSchema` — rejected: the issue specifically wants exactly one narrowed retry; a configurable knob risks recreating the original bug by being turned back up.
- Keep retrying automatically with no hard ceiling, narrowing scope indefinitely — rejected: unbounded automatic narrowing is itself a way to quietly keep burning tokens on a Task that's fundamentally too big; a human should see it after the second Exhausted Run, not after an unbounded chain of ever-smaller automatic attempts.
