# search_threads has no database-level access boundary — only prompt wording

`amazing-hashbrown` has no multi-user/ownership model, so `search_threads(threadId)` can open any thread in the database — active or archived, any workspace, any thread type — once a caller supplies a valid id. "Don't use this unless you already know the id" and "never search your own thread" are enforced only by the tool's description/system-prompt wording and an explicit self-thread refusal check against `config.configurable.thread_id` — not by any ownership check against the calling thread or workspace. We accepted this because there is no real boundary to enforce in a single-local-user app; teaching the tool "which threads a caller owns" would be complexity added against a threat that doesn't exist here.
