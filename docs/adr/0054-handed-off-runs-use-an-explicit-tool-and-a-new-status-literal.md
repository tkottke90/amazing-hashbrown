# Handed-off runs get an explicit tool and a new status literal, not inferred detection or a side field

Issue #364: a Run that cooperatively stops mid-HITL at the user's request, leaving a real summary, was indistinguishable from a genuine stall or crash — both landed as `task_queue.status: 'failed'`, skewing retrospective failure counts and letting the harness overwrite the agent's actual summary with a canned "ran out of steps" message.

We considered inferring this case after the fact (e.g. "this Task was paused for HITL earlier, and the final message reads like a summary") instead of giving the agent an explicit tool to call. Rejected: inference from free text is the same kind of heuristic that produces misclassified Runs today, and this is LLM-facing behavior either way — it needs an eval scenario under this repo's EDD rules regardless of which path is chosen, so inference buys no implementation shortcut, only a less reliable signal.

Decided: add exactly one new outcome value (named `handed_off`) to the existing `task_queue.status` (and `RunOutcome`) union — not a separate side field/flag alongside `status: 'failed'` — produced only when the agent explicitly calls a new tool, `hand_off_task` (a sibling to `complete_task`). This new status is treated as finished and transcript-readable alongside `done`/`failed`/`cancelled`, and is excluded from `failedRunStreaks()`'s failure count while remaining its own visible signal in retrospectives, rather than disappearing from them.

**`hand_off_task` is unconditionally present in a task Run's tool list**, exactly like `complete_task` and `ask_user` already are, rather than hidden until a HITL interrupt has fired. No existing mechanism gates a tool on same-Run history the way this would need (the Skill-Gated Tools middleware gates on active skill, not run state), and building one for a single tool is the kind of bespoke, generic-for-one-case machinery this repo's design principles warn against — the existing tools already prove the simpler trust model works. Instead, `hand_off_task` reuses `complete_task`'s own proven pattern: a nudge-once call-time check that rejects the first call if no `ask_user` interrupt has occurred yet in that Run (pointing the agent at `complete_task`/`ask_user` instead) and accepts unconditionally after that. The check reads `task_queue.pause_reason === 'chat'` on the current row — already left in place, uncleared, by `resumePausedEntry()` specifically so a later step in the same Run can still see that a HITL pause happened.

**The owning Task settles to `blocked`, not `handed_off` or `failed`.** `settleTaskAfterRun()` normally writes a Run's outcome straight into `tasks.status` verbatim; `handed_off` is special-cased to `blocked` instead, since `blocked` already exists, the board already renders it, and it doesn't re-introduce at the Task level the exact "stopped ≠ failed" mislabeling this ADR exists to fix at the Run level.
