# HITL interrupt spans are detected by the thrown error's `name`, not by tool name or error-text matching

Issue #404: `ask_user`/`shell_exec` calling LangGraph's `interrupt()` throws a `GraphInterrupt` *inside* the tool function, which `ObservabilityCallbackHandler.handleToolError` (api/src/agents/observability-handler.ts) records as an ordinary errored span — before the throw ever reaches `recoverThrownInterrupt`, the code that correctly treats it as a successful HITL pause rather than a turn failure. This inflates `lib/thread-reports`' `failureCount`/Failure Breakdown and renders the span with error styling.

We considered fixing this at report-build time in `lib/thread-reports/src/build.ts` instead — treating any errored `tool-call` span named `ask_user`/`shell_exec` as non-failure. That would need no schema change and would retroactively repair already-recorded historical spans (including the issue's own motivating gmail-labeler2 thread). Rejected: it's a guess by tool name, not by cause — a genuine future failure inside either tool would also be silently excluded from failure counts, and every new interrupt-capable tool would need this list maintained by hand. ADR-0069/ADR-0070 already rejected this same shape of guess (text/name matching in place of a structural signal) for this exact Failure Breakdown feature.

Decided: detect the interrupt at its origin, `handleToolError`, by checking `err.name === 'GraphInterrupt'` — the same convention this codebase already uses everywhere else it identifies this error (`stream-handler.ts`, `task-execution.ts`, the loop guard), chosen there specifically because `instanceof` doesn't survive `PipeEventsError`'s wrapping. Record the result as a new `interrupted: boolean` field on `SpanRecord` (default `false`), leaving `error: null` for an interrupted span — so `lib/thread-reports`' existing `error !== null` failure logic excludes it with no changes of its own, for any current or future tool that calls `interrupt()`, with no hardcoded tool-name list anywhere.

**Consequence**: this does not repair already-recorded spans from before the fix — a historical thread report (e.g. the gmail-labeler2 example in #404) keeps showing its old, inflated counts unless regenerated. Thread Reports are built fresh from stored spans on each request rather than persisted, so no backfill migration exists to reclassify old rows; accepted as the cost of not papering over real bugs with a name-based guess.
