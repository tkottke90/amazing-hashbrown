# Turn Overflow recovers via automatic truncation, not a HITL interrupt

While designing the fix for #354 (a Turn Overflow — a single Turn's own tool-call history exceeding `boundaryAwareTrim`'s budget before any trimming even runs — could silently drop the user's message entirely), we considered reusing `RecursionGuardMiddleware`'s existing pattern: pause via LangGraph's `interrupt()` and ask the user to choose "Continue working" or "Stop and summarize," exactly as it already does for step-limit and stagnation detection. We rejected that for this specific failure: pausing to ask is tolerable for recursion/stagnation because loops are rare, but a single oversized tool result (a full page fetch, a large JSON dump) is not rare, and interrupting on every such Turn would make the system frustrating to use for any workflow that regularly produces large tool output. Instead, `boundaryAwareTrim` now tries first to make the Turn fit automatically — truncating the largest `ToolMessage`(s) in place and offloading the removed content through the existing `toolStub`/`storeToolContent` mechanism so it stays retrievable via `get_tool_key` — and only escalates when even truncating every tool message to a minimal stub still doesn't fit: the same rare tier of problem `MIN_BUDGET_FLOOR` already treats as a misconfiguration today. That escalation is a plain `context_length`-classified error for interactive/task runs and a thrown `ContextBudgetExceededError` for sub-agent runs, never an interrupt.

## Considered Options

- Reuse `RecursionGuardMiddleware`'s `interrupt()`-based "Continue working / Stop and summarize" pattern verbatim — rejected: large single-Turn tool output is common enough that this would interrupt routinely, not rarely, making the system frustrating for normal use.
- Always escalate with a plain error and no automatic recovery attempt — rejected: would turn an ordinary large-fetch Turn into a failed turn the user must retry, when the content can usually just be trimmed/offloaded safely instead.
