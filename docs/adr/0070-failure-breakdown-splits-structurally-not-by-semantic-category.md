# Failure Breakdown splits structurally (span type + tool name), not into a semantic error taxonomy

Issue #401 proposed a "failure taxonomy (distinct error strings/categories with counts)." We considered pattern-matching raw error text into semantic categories, including a dedicated "MCP/tool-disconnect" bucket the issue's own example (disconnected MCP tools) suggested. Rejected after checking: `span.error`/`trace.error` are 100% raw `err.message` text with no categorization ever persisted — the structured `ChatErrorCategory` enum (`api/src/agents/error-classification.ts`) is computed live for SSE events only and never stored — and no literal string exists anywhere for "MCP disconnected" specifically, since that text comes straight from the MCP SDK's own unpredictable error.

Decided: split failures structurally by the one thing that _is_ reliably persisted — `span.type` (`tool-call`, keyed further by `span.name`/tool name; `llm-call`; `attachment`) or "turn-level" for a `trace.error` with no owning span — with exactly one literal substring match (`ContextBudgetExceededError`'s fixed message, thrown at the turn level per `api/src/agents/summary-boundary.ts`) promoted to its own `context_length` category. Everything else that doesn't match is left as `other`, with one example message, rather than forcing it into a guessed label.
