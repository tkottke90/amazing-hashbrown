# `taskState` Command writes merge via a channel reducer and persist once per step, not per-tool

Fixing issue #362 (`InvalidUpdateError` on the `taskState` channel): `write_task_note` and `update_plan` each read `taskState`, computed a full next-state snapshot, and returned a `Command` writing it back — fine when only one of them runs, but if the model calls both in the same turn, LangGraph runs them as parallel branches in the same superstep and the `taskState` channel (a plain Zod field, implicitly a last-value channel) threw because it received two writes in one step. A reducer alone wasn't enough: each tool also called `writeTaskFile()` directly from its own body, computed from the same stale pre-step snapshot — an independent lost-update race on the Task File itself that a reducer on the graph channel does nothing to fix, and that fixing the crash would otherwise turn into _silent_ note loss on disk. We gave `taskState` a proper LangGraph reducer (`withLangGraph`, the same mechanism `messages`/`addMessages` already uses) so both tools send a small append-only delta instead of a full snapshot, and moved the Task File's disk write out of each tool's body into two middleware hooks — `beforeModel` and `afterAgent` — that run once per step, after the channel has actually been reduced, rather than once per tool call. That combination is the only one that sees the merged state: `afterModel` fires before tools run at all, and `wrapToolCall` sees each call's state before this step's writes are reduced.

## Considered Options

- Lock/serialize the existing per-tool `writeTaskFile()` calls — rejected: a lock only prevents a torn file write, not the lost update itself, since each tool's computed next-state is already wrong (built from a stale base) before any lock is taken.
- A dedicated graph node inserted after the tools node to do the single disk write — rejected in favor of `beforeModel` + `afterAgent`, which covers the same cases (including a `return_direct` tool skipping the loop-back edge) without adding custom graph wiring on top of this codebase's existing middleware composition.

## Consequences

Supersedes [ADR-0037](./0037-task-file-writes-are-direct-inline-calls.md) for `write_task_note` and `update_plan` specifically — those two no longer write the Task File inline. ADR-0037's own reasoning (Task Goal and Handoff Notes are produced by `task-execution.ts` outside the tool-call loop, so one hook can't cover every write site) still holds for the orchestrator's pre-Run/post-Run writes, which are unaffected and stay direct inline calls. A future tool that reads or writes `taskState` needs to go through the same delta shape and reducer, and a reader needs both hooks in view, not one obvious write site, to see the full persistence path.
