# Task File writes are direct calls from each state-changing site, not a middleware

`update_plan` already performs its own side effects (DB patch, broadcast) inline rather than through a generic composition layer. We followed the same precedent for Task Files: `write_task_note`, `update_plan`, and the task-execution orchestrator's pre-Run and post-Run steps each call one shared render-and-atomic-write utility directly, right after they change Task State. We considered a generic "sync on state change" middleware instead, so no individual tool would need to know a Task File exists, but rejected it — Task Goal and Handoff Notes are produced outside the agent's own tool-call loop entirely (by the orchestrator, before and after a Run), so a single middleware hook couldn't cover every write site anyway, and splitting the mechanism in two would be more complex than just calling the shared utility from all four sites directly.
