# MCP tools are default-off and granted per-Turn via discovery, not bound with their server

**Status:** accepted

Connecting an MCP server used to mean every one of its tools was bound to every Turn of every thread that enabled it — fine for a handful of tools, costly for a server with dozens (61 schemas / ~11,900 prompt tokens observed for one server, paid on every turn regardless of relevance, hitting local-model providers hardest). We changed the default so an MCP tool is not bound unless a user has explicitly customized it on, and added two always-on tools (`search_mcp_tools`, `use_mcp_tools`) that let the model find and grant itself access to a specific tool mid-conversation. A grant lasts only for the rest of the current Turn (GLOSSARY.md's existing Turn boundary) — it is not sticky across Turns, and is not merged into the existing `#tool-name` mechanism, which was deliberately specced (2026-09-14) to never force-bind a tool outside what's already offered. The recurring/named-workflow case (a skill that always wants a specific MCP tool) is explicitly left to a skill-declared-gating mechanism (#409), not solved here — a Turn-scoped grant that doesn't carry forward is the right trade-off for the ad hoc case this solves, and the wrong one for a recurring workflow, which is why that's a separate mechanism rather than a longer-lived version of this one.

A second, less obvious consequence: sub-agent runs previously scoped every tool — including MCP tools — through one static, build-time allowlist (`getSubAgentToolIds()`), with no per-call discovery of any kind. Reaching the same default-off-but-discoverable behavior there meant pulling MCP tools out of that build-time allowlist entirely and structurally including the full MCP candidate set the same way chat/workspace/task agents already do, relying on the new per-call discovery middleware instead. Built-in tools keep going through the static allowlist unchanged; only MCP tools moved. A future reader seeing MCP tools absent from `getSubAgentToolIds()`'s filtering should not assume that's an oversight — it's deliberate, so a sub-agent gets a path to the MCP catalog via discovery rather than none at all.

See `docs/superpowers/specs/2026-11-11-mcp-tool-discovery-design.md` for the full design and the rest of the settled decisions.
