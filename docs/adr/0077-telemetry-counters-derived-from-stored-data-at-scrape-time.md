# Telemetry counters are derived from stored data at scrape time, not incremented as usage happens

The Telemetry Endpoint (`GET /metrics`) exposes token, cost, tool-call and tool-failure counters for Prometheus. Each value is the cumulative total already held in `CostStore` / `ObservabilityStore`, recomputed on every scrape: each `Counter`'s synchronous `collect()` resets it and re-applies the stored total (`api/src/services/telemetry/`).

We considered the conventional alternative — in-process counters incremented at the moment usage is recorded. Rejected: it needs a hook in the turn-observability write path (`finalizeTurn` and the observability callback handler), coupling Telemetry to code that has other jobs; every restart resets each series to zero, so the first scrape after a deploy has no history; and the numbers would be a second, independently-maintained tally that can drift from the dashboard's. Deriving from the stores gives restart-safe counters, an immediate backfill of all history on the first scrape, and the same figures the dashboard widgets show.

Decided: derive at scrape time, using one synchronous `collect()` per counter so two overlapping scrapes can't interleave the reset and the increments. Token and cost rows are read over the full date range (`1970-01-01`–`9999-12-31`), not "up to today" as the dashboard Metrics do, so a row dated ahead of UTC is never hidden and then added later.

**Consequences**: a Prometheus counter must never go down, and this holds only while usage rows and tool-call spans are never deleted. Nothing in this repo prunes them today; if retention is ever added, a scraped counter will drop and Prometheus will read it as a restart (rates stay correct, but `increase()` over that window will under-count). Each scrape runs full aggregations — cheap at this app's size (daily rows per provider/model, one row per tool); if that stops being true, cache the result for a few seconds rather than change the model. Skill usage (#451) has no persisted source to derive from, so it may become the first counter that is incremented in-process instead.
