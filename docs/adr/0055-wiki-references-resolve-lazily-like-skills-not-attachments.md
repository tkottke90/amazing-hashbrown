# Wiki References resolve lazily, following Skill Expansion's pattern, not Attachment's eager resolution

This codebase already has two precedents for getting external content in front of the model on a turn: an Attachment is resolved eagerly, in the chat route handler's `resolveAttachmentsForTurn`, before that turn's HumanMessage is even persisted; a Skill is resolved lazily, inside a `beforeAgent` middleware (`skill-expansion.middleware.ts`), reading the skill's body from disk only once that turn is actually invoked by the agent, while the checkpoint keeps the raw `/command` text forever. A Wiki Reference follows the Skill pattern: a new `beforeAgent` middleware reads the referenced page from the wiki store only at turn-invocation time, and the persisted thread record never carries more than the Wiki Reference's own `{Wiki Domain, path, title}` tuple. Resolving this late means the page is read fresh on every invocation of that turn — including a retry or regenerate, which re-enters the same `beforeAgent` step — rather than once, upstream, at the moment the message was first sent; it's also what makes a page deleted out from under a staged reference a plain in-context "page no longer exists" notation instead of a failure the route handler has to pre-empt.

## Considered Options

- Resolving the page eagerly in the chat route handler, mirroring Attachment's pipeline — rejected: it would read the page's content at message-construction time regardless of whether that turn's agent invocation ever runs, and would need the resolved body (or an `UserMessageAttachment`-style exclusion record) committed to the persisted turn immediately, which is exactly the standing copy a Wiki Reference is designed never to keep.
