# Failure Breakdown sources trace/span error text, not the assistant message's error field

Issue #401: the workspace-retrospective narrative had only aggregate failure/tool-call counts to reason from, so it fabricated a cause that matched the workspace's goal text instead of what actually happened. We considered sourcing the new Failure Breakdown from `AssistantPayload.error` — the thread message store's own typed "why did this message fail" field — since it already exists for exactly this purpose. Rejected: tracing the real call paths (`api/src/agents/stream-handler.ts` and its siblings) shows a turn-ending failure writes the same classified message to both `AssistantPayload.error` and `trace.error` in the same catch block, so the assistant field adds no information the trace doesn't already have — and it only ever fires when a whole turn ends in error, missing every tool-call failure a turn survives and continues past. That's exactly the case issue #401 is about (fetch timeouts and MCP tool failures mid-turn, with the turn carrying on).

Decided: compute the Failure Breakdown entirely from `TraceWithSpans`' `trace.error`/`span.error` — the same source `build.ts`'s existing `failureCount` already uses — as a new field on the shared `ThreadReportStats` type rather than private to the narrative builder, so the standalone Thread Report page gets the same detail for free instead of re-deriving it per consumer.
