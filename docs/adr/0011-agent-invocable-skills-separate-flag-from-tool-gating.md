# Agent-Invocable Skills get their own tool flag, not the existing `autonomous` one

Skills today only expand off a literal human-typed `/command` (`skill-expansion.middleware.ts`), so a Skill whose knowledge is only occasionally relevant (app configuration, workspace setup, etc.) can't be reached by the agent on its own — it either sits in the system prompt unconditionally or doesn't get used. We're introducing **Agent-Invocable Skills**: a Skill property, plus a new `invoke_skill` tool (lookup-then-return-content, same shape as `wiki_read_page`) that lets the agent fetch one on its own initiative. A Skill that also gates tools (`skill-gated-tools.middleware.ts`) may be Agent-Invocable, but invoking it this way only exposes the gated tools that individually carry a new `agentExposable` per-tool setting (parallel to the existing `defaultInclude: { chat, subAgent, autonomous }` in `api/src/agents/tool-config.ts`) — any gated tool without it stays hidden even while the Skill's gate is otherwise open, so the agent can never self-grant access to a tool nobody explicitly marked safe for that path.

## Considered Options

- Reuse the existing `autonomous` flag as the signal for which gated tools may be exposed via self-invocation — rejected: `autonomous` governs whether `buildTaskAgent`'s unattended/headless runs may use a tool at all (a presence-of-a-human axis), not whether the agent may grant itself that tool mid-chat without an explicit command (a self-escalation axis). The design spec's own example config sets `shell_exec: { autonomous: true }` for reasons unrelated to self-invocation risk; reusing the flag would make `shell_exec` agent-self-invocable as a side effect.
- Trigger skill expansion off the agent's own message (teach the model to emit `/command` itself) instead of a new tool — rejected: reuses existing plumbing, but depends on reliable instruction-following for a specific text pattern rather than a tool call, which is a weaker guarantee; the current wiki tools already establish the lookup-tool shape as this app's standard pattern for on-demand knowledge.
- Make Agent-Invocable and Gated mutually exclusive outright — rejected: unnecessarily forecloses a Skill combining both, when a per-tool override can make the combination safe on a tool-by-tool basis.
