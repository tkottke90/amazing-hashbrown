# Sub-Agent Task titles generate asynchronously, via a one-shot LLM call, and fall back to truncation on any failure

Sub-Agent Tasks (created by `spawn_sub_agent`) previously copied the full `goal` instruction verbatim into `Task.title`, with `description` left null — the cause of the excessively long chat-bubble and thread-header text reported as a UI bug. We now keep the full instruction in `description` (reusing the `title`/`description` split every other Task type already has) and generate a short `title` via a dedicated one-shot LLM call, following the existing `generateTitleHandler`/`rewriteTaskForHandOffGuidance` convention (`resolveTurnModel` → `startTurnObservability` → `model.invoke` → `turnObs.end`) so it is correctly cost-tracked like every other one-shot call in `agents/`.

We considered having the spawning agent supply a short title itself, alongside `goal`, matching how `create_tasks` already works — rejected because it puts summarization burden back on the parent agent, which this design is specifically trying to avoid. We considered mechanical truncation of `goal` alone — rejected as the primary mechanism because it produces awkward mid-sentence cutoffs; it remains the fallback.

The generation call runs **after** `createSubAgentTask` returns, not before it. Dispatch already "returns immediately, without awaiting any of their Runs," and a Run only starts once the task queue picks it up — a delay that in practice is almost always longer than a title-generation round-trip, so the generated title reaches the user before the Run's own thread/marker message are even created. `createSubAgentTask` returns immediately with a mechanical-truncation placeholder as `title`; the generated title overwrites it once ready. The call uses `env.defaultProvider` (the system default), not the Sub-Agent Task's own Role — that Role isn't resolved until the Run starts, and reusing it would mean constructing a model twice and risks spending an expensive model's call budget just to write a title, undercutting the cost-consciousness behind generating one at all. On any error or timeout, it falls back silently to the truncation placeholder and never blocks or fails the Dispatch call — deliberately the opposite of Hand-Off Guidance's existing "surface an error rather than falling back" precedent (ADR-0057), which is appropriate there because it is a deliberate, user-initiated save action; here the generation step is invisible background work, where availability matters more than the title being LLM-written.
