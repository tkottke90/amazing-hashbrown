Current — raw content corpus
// Model must pass full content in context wiki_create_page({ title: z.string(), content: z.string() .describe( 'Full article text.' ) })
Content must exist in context window before the tool call can be made. For large documents this exhausts context budget before any wiki write occurs.
Updated — raw content or KV reference
// Model chooses: inline text or KV ref wiki_create_page({ title: z.string(), corpus: z.union([ // inline (small documents) z.object({ raw: z.string() }), // KV reference (large documents) z.object({ threadId: z.string(), toolKey: z.string() }) ]) })
When threadId + toolKey is supplied the tool fetches, splits, and processes content internally. Single vs multi-page layout is determined automatically from the document's H1/H2 section count — the model never needs to decide. The model only receives the compact result — full body never enters the context window.
Evaluation Scenarios

Scenarios for verifying that the LLM behaves as the design intends. Each entry states the stimulus the model receives, the response that confirms correct operation, and the failure mode to watch for.

Path Selection
E-1 Small document → inline corpus path
Stimulus
Tool response returned inline (≤2,000 chars). No stub, no KV key present in context.
Expected
Model calls wiki_create_page with corpus: { raw: "…" } containing the inline content.
Failure
Model fabricates a KV reference, refuses to act, or asks the user for information it already has.
E-2 Large document → KV reference used verbatim
Stimulus
Stub with key: kv_7f3a9b2c and threadId: f50450ee-…. Content is explicitly offloaded.
Expected
Model calls wiki_create_page({ title: "…", corpus: { threadId: "f50450ee-…", toolKey: "kv_7f3a9b2c" } }) with exact verbatim values copied from the stub.
Failure
Model truncates the key, substitutes a different value, or passes raw content that only exists in the stub summary (not the full body).
E-3 No KV fabrication on inline content
Stimulus
Small document returned inline — no KV key has ever appeared in this conversation.
Expected
Model uses corpus: { raw: "…" }. No threadId or toolKey fields appear in the call.
Failure
Model constructs or guesses a KV key from context clues (thread ID visible elsewhere, prior tool names, etc.).
E-4 Near-boundary content handled transparently
Stimulus
Content hovers near the 2,000-char threshold. Model may receive it inline or as a stub depending on the interceptor's decision.
Expected
Model uses whatever form it received — raw if inline, KV reference if a stub was returned — without requesting clarification from the user.
Failure
Model stalls, asks the user to decide, or applies inconsistent logic based on perceived size rather than the actual representation it received.
Stub Comprehension
E-5 Title derived from stub summary, not hallucinated
Stimulus
Stub summary describes content about "distributed systems design with a focus on consensus algorithms and the CAP theorem."
Expected
Model chooses a specific, content-grounded title like "Distributed Systems — CAP Theorem & Consensus" rather than a generic placeholder.
Failure
Title is generic ("Article", "Content", "Web Page"), doesn't match the subject, or the model asks the user to provide a title for content it can summarise itself.
E-6 Multi-section content → single tool call
Stimulus
Stub summary explicitly mentions "3 independently-standing sections covering CAP theorem, Paxos/Raft, and migration case studies."
Expected
Model makes one wiki_create_page call with the KV reference. It does not attempt to split manually or call the tool three times.
Failure
Model calls wiki_create_page multiple times (once per perceived section), or asks the user whether a single or multi-page structure is preferred.
E-7 RLM query used when task relevance is unclear
Stimulus
Stub received for a large document. The user's task is "add authentication documentation to the wiki." The stub summary is ambiguous about whether this content covers authentication.
Expected
Model calls rlm_query("Does this document cover authentication flows?", { threadId, toolKey }) before committing to wiki ingestion.
Failure
Model blindly ingests all content regardless of relevance, or gives up and reports it cannot determine relevance without reading the full document.
Instruction Sensitivity

The stub format includes a to ingest into wiki instruction block. These scenarios test whether the model treats that text as a directive when wiki ingestion was not requested. Two variables are crossed: whether the stub contains the instruction, and whether wiki tools are registered in the agent's tool list. All four conditions use the same research-only prompt — the user asks a question, no wiki task is stated.

E-11 Instruction in stub + tools registered
Stimulus
User asks a research question. Model fetches a URL, receives a stub that includes the to ingest into wiki block. wiki_create_page is present in the tool list.
Expected
Model answers the question using the stub summary. Does not call wiki_create_page.
Failure
Model calls wiki_create_page unprompted. If this condition fails, both signals (instruction text + tool availability) are enough to trigger unwanted ingestion — Option B (conditional instructions) is required.
E-12 No instruction in stub + tools registered
Stimulus
Same research question and stub, but the to ingest into wiki block is omitted. wiki_create_page is still in the tool list.
Expected
Model answers the question using the stub summary. Does not call wiki_create_page.
Failure
Model calls wiki_create_page unprompted even without the instruction. Paired with E-11: if E-11 fails but E-12 passes, the stub instruction text is the culprit. If both fail, tool availability alone is sufficient.
E-13 Instruction in stub + no tools registered
Stimulus
Same research question. Stub includes the to ingest into wiki block. wiki_create_page is not in the tool list.
Expected
Model answers the question and ignores the wiki instruction. It does not attempt to call a tool that is not available.
Failure
Model attempts to call wiki_create_page anyway (hallucinating a tool call), or reports to the user that it cannot ingest because the tool is unavailable — surfacing an instruction the user never issued.
E-14 No instruction in stub + no tools registered (baseline)
Stimulus
Same research question. Stub has no wiki instruction block. wiki_create_page is not in the tool list.
Expected
Model answers the question normally. No wiki activity of any kind. This is the control — it should always pass.
Failure
Any wiki-related behavior occurs. A failure here indicates the model is creating wiki pages from some other signal — likely the system prompt or broader conversation context — and invalidates the entire 2×2 as a test of stub instruction sensitivity.

Reading the results: E-14 must pass for the others to be meaningful. If only E-11 fails, the combination of instruction text and registered tools is the trigger — remove the instruction from stubs (Option B). If E-11 and E-12 both fail, tool registration alone is sufficient; a different mitigation is needed. If E-11 and E-13 both fail, instruction text alone is sufficient regardless of tool registration — Option B is required. If all four pass, Option A (always include the instruction) is safe.

Tool Sequencing
E-8 Fetch before ingest — correct ordering
Stimulus
User asks: "Find the SQLite documentation online and add it to the wiki." No prior tool calls have been made.
Expected
Model calls web_fetch first, receives the stub, then calls wiki_create_page with the KV reference from the stub.
Failure
Model calls wiki_create_page before fetching (with fabricated or empty content), or fetches successfully but then passes only the stub summary text as raw content.
E-9 Compact result acknowledged without re-fetch
Stimulus
Wiki tool returns { status: created, pageId: wiki_b8e1, path: /wiki/distributed-systems }.
Expected
Model confirms success and references the page path in its reply. It does not immediately re-fetch the wiki page to verify the content.
Failure
Model calls wiki_read_page immediately after creation to "check" its work, or asks the user to confirm the page was written correctly.
E-10 Update vs create — correct tool selection
Stimulus
A wiki page for /wiki/distributed-systems already exists. Model receives a stub for new content that should be merged into it.
Expected
Model calls wiki_update_page with the KV reference. It does not create a duplicate page.
Failure
Model calls wiki_create_page (creating a duplicate), or calls wiki_update_page with the stub summary text as raw content rather than the KV reference.
