Overview

The Collaboration System introduces three first-class entities that sit between the user and the LLM-wiki layer. Together they answer two questions the wiki alone cannot: where is work happening, and what needs to be done next.

The wiki remains the long-term knowledge layer — stable, synthesized, LLM-maintained. The collaboration system is the operational layer: mutable, scoped, and tied to goals that can be completed or abandoned.

Core distinction: Wikis accumulate knowledge that compounds over time. Workspaces are sandboxes where that knowledge is applied to a goal. Tasks are discrete units of work inside (or independent of) those sandboxes. Projects wrap all three into a goal-bounded unit with a formal close process.

Core Concepts

Foundation

Workspace

A sandboxed directory with a defined goal. Can be wiki-bound, git-connected, and long-lived. Both user and agent edit files directly — unlike wikis, there is no LLM-only write restriction. Supports dependency isolation per language (venv, node_modules).

Work Tracking

Task

A discrete unit of work assigned to user or agent. Trigger-driven, Kanban-tracked, and optionally synced to an external tracker (Todoist, GitHub Issues). Can belong to a workspace or sit in the global user inbox when unassigned.

Goal-Bounded

Project

A workspace with a dedicated ephemeral wiki and an explicit win condition. Agent writes go only to the project wiki. Requires a formal close — wiki is snapshotted into the workspace directory and selected pages are merged into persistent domains.

What separates a Project from a Workspace

A project is a workspace — the projects table extends workspaces 1:1. The distinguishing attributes are:

  • Dedicated ephemeral wiki — created at project start, archived at project close
  • Explicit win condition — natural language and/or requirements list; project must close or be explicitly abandoned
  • Write scope restriction — agent writes go only to the project wiki, enforced at the tool level (hard guardrail, not a prompt instruction)

Regular workspaces have a directional goal but no win condition, no dedicated wiki, and can live indefinitely.

The global user inbox

Tasks with no workspace assignment belong to the global user inbox. The inbox is not a workspace — it has no schema record, no directory, no goal statement. It is simply the default bucket for unassigned tasks, surfaced in the UI as a flat task list.

Task Execution Runtime

Task execution is queue-based and serial. The queue is the task_queue table — not an in-memory structure. A server restart recovers queue state from the DB.

Priority rule: chat preempts the queue

When the user sends a chat message, the queue pauses (running item moves to paused status). The queue resumes 30 seconds after the last chat response. Whether LangGraph's interrupt() mechanism can checkpoint a paused agent task is an open implementation question worth investigating before building a custom pause mechanism.

Two operational endpoints support the queue:

  • GET /api/v1/tasks/queue — lists queued and scheduled tasks with position and status
  • SSE event task_queue_update — signals when a task begins or completes execution

Trigger types

Chat User or agent explicitly enqueues during a conversation. Added immediately with the next available position.
Cron (one-time) Enqueued at a specific datetime stored in trigger_config. Fires once; entry remains as a record.
Cron (repeating) Enqueues on a schedule. The final step of each run is to enqueue the next iteration. Respects max_iterations and stop_after in trigger_config.
Webhook POST /api/v1/triggers/webhook/:id enqueues the task. Useful for CI completion, external alerts, or any event-driven source.

Wiki Binding & Write Scope

Every workspace can be bound to a wiki domain. That binding sets the first lookup — not an exclusive scope. The agent falls through to wiki_locate for anything the bound wiki cannot answer. Read scope is always broad.

Write scope adds a project-specific restriction: in a project, agent writes go only to the project's ephemeral wiki. This is a hard guardrail enforced at the tool level — the scoped variant of wiki_create_page / wiki_update_page is preconfigured with the allowed target domain. Calls targeting other domains are rejected by the tool, not by a prompt instruction.

In a project, the agent can read from the homelab wiki to synthesize context while writing into the project wiki. It cannot write back to homelab mid-project. Those writes happen only at project close, through the selective merge step, under user direction.

External tracker state mapping

The adapter interface defines a set of canonical task states. Each adapter implementation maps its system's native states to those definitions. The tasks table stores only canonical state — the adapter owns the translation in both directions.

pending / backlog ready in_progress waiting_on_user blocked done failed / cancelled

Example: Todoist uses <Project>/<Section> for state; GitHub uses labels or Project column status. Each adapter maps those to the canonical states above.

Project Lifecycle

Wiki snapshot format

In a git-connected workspace: snapshot is committed as a wiki/ directory alongside a version tag (e.g., v1.0.0). In a non-git workspace: timestamped directory copy (wiki-snapshot-2026-08-14/). A subsequent project on the same workspace overwrites the prior snapshot.

Ephemeral domain archival

On project close, two independent checks enforce the archived state:

  • DB check — wiki_domains.domain_status = 'archived' checked at the API layer before any write tool executes
  • Frontmatter check — status: archived in index.md checked by the wiki SDK before any commitPage() call

Both must reject writes independently. Either path alone is not sufficient.

Workspace & Project Creation

Two entry points; one underlying process. The UI form calls the same agent skill invocation under the hood — the form provides structured up-front context so the agent does not need to ask as many questions.

Chat skill

User types /create-workspace or /create-project. The built-in skill contains the setup questions, scaffolding instructions, and scripts for creating the directory structure. Works in any chat context.

UI form

Lives on the dedicated Workspaces page. Collects name, goal, location, wiki binding, git options, and (for projects) win condition up-front, then submits as a structured skill invocation. Same process, less back-and-forth.

Both paths create the workspaces record, scaffold the directory under WORKSPACE_ROOT, and (for projects) create the ephemeral wiki domain and the projects record. Win condition is a required field for projects and is defined at creation time, not after.

Design Rules

These invariants must be preserved by every implementation decision. If a code change violates one, the change is wrong — not the rule.

  • R1A workspace is the base unit. A project is a workspace — the projects table extends workspaces 1:1. No separate routing, no duplicated fields.
  • R2Wiki binding sets the first lookup, not an exclusive scope. Agents fall through to wiki_locate when the bound wiki returns nothing. Read scope is always broad.
  • R3In a project, agent writes go only to the project's ephemeral wiki. This is a hard guardrail enforced at the tool level — not a prompt instruction.
  • R4The task queue is serial. One item runs at a time. Chat preempts; the queue resumes 30 seconds after the last chat response.
  • R5The queue is the task_queue table. There is no separate in-memory queue. Server restart reads the table and resumes from where it left off.
  • R6Triggers are attributes of tasks, not separate entities. A repeating cron task enqueues its next iteration as the final step of its own execution.
  • R7External tracker sync uses canonical state definitions. Each adapter maps its system's native states to those definitions. The tasks table stores only canonical state.
  • R8Workspace file access is sandboxed to the workspace's location directory. The filesystem tool must reject any path traversal above that boundary.
  • R9Agent git authority is collaborator-level: normal operations (checkout, pull, push, fetch, rebase) are permitted; history-rewriting operations (reset --hard, force-push to default branch) are not.
  • R10Projects require a formal close. Abandoned projects must be explicitly marked abandoned. There is no automatic expiry or timeout.
  • R11An archived ephemeral wiki domain must reject writes through both the API DB check and the wiki SDK frontmatter check. Either path alone is insufficient.
  • R12Unassigned tasks belong to the global user inbox. The inbox is not a workspace and has no schema record — it is the UI view of tasks where workspace_id IS NULL.
  • R13Workspace-scoped chat gets its own system prompt that injects workspace context (goal, bound wiki, write scope rules) at session start. This is the mechanism for context propagation, not a runtime lookup.
