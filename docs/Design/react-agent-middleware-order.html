What createAgent() builds, and in what order

Four builders in chat-agent.ts all call LangChain's createAgent(). The loop itself lives in that library's ReAct graph — this codebase only shapes what goes in and plugs into three hook points along the way.

Why this shape matters for #403

  • There's no fourth hook family. LangChain's middleware gives this codebase exactly four insertion points — once-at-start, once-at-end, and two per-iteration hooks. A mid-loop compactor has to be one more beforeModel or wrapModelCall entry; there's no separate "after each tool result" hook to attach to.
  • ContextWindow already proves the pattern works. It's the only middleware here that runs in two hook stages and reads the accumulating message list on every single loop pass — which is exactly the access a summarizer would need. The gap isn't access, it's that both of its passes are reactive truncation (boundaryAwareTrim / recoverTurnOverflow), never proactive summarization.
  • Position isn't fixed across agent types. In the Chat/Workspace/Task tuple, ContextWindow sits near the inner end of the wrapModelCall onion (position 15 of 17, just before the innermost ModelInputSnapshot). In the Sub-agent's shorter tuple it's the outermost wrapModelCall layer. Any new compaction middleware needs to pick its array position deliberately per builder, not assume one relative order.
  • Sub-agent runs have no afterAgent exit hook at all (deliberately, per ADR-0063) — so whatever #403 adds has to do its real work inside the loop body, not lean on a turn-end hook the way the wiki-write pipeline does.

The same thing, as a call tree

The bands above group by hook type; these group by what actually contains what. beforeAgent/beforeModel/afterAgent entries are just a numbered sequence — siblings that each run and return. wrapModelCall entries are different: each one is a function that receives the next one as its handler argument, so the array becomes a single chain of one-child nodes, each literally wrapping the next, bottoming out at the real model.invoke().

Both trees below now also carry where a new HistoryCompaction middleware for issue #403 would slot in (dashed, green — nothing with that name exists yet). It only needs a beforeModel hook, placed immediately before ContextWindow's own beforeModel stage: late enough that it's working with whatever the rest of beforeModel already did to the message list, early enough that ContextWindow's trim is always the last line of defense, never the first. It gets no wrapModelCall stage and never touches the onion.
