# Undici Headers-Timeout Safety Net for LLM Providers (Issue #402) — Design

**Date:** 2026-11-10
**Status:** Draft
**Related:** [Issue #402](https://github.com/tkottke90/amazing-hashbrown/issues/402), [ADR-0062](../../adr/0062-headers-timeout-derived-from-timeoutms-not-its-own-field.md)

---

## Goal

Stop a configured provider's `timeoutMs` from being pre-empted by undici's shorter default `headersTimeout` (300s), which is the confirmed root cause of 19 of the 40 logged failures in the gmail-labeler2 retrospective thread (`0427ff19-934c-49dc-9f24-234194263862`), all the identical "Node.js fetch timed out waiting for response headers" error against a Digital Ocean/glm-5.3-flash endpoint.

---

## Problem

Node's global `fetch` dispatches through undici's default `Agent`, whose `headersTimeout` defaults to 300s. `createProviderFromConfig()` (`api/src/services/provider-factory.ts`) already forwards a provider's optional `timeoutMs` to the underlying SDK's own `timeout`/`clientOptions.timeout`, but nothing in this codebase sets undici's `headersTimeout` to match. When `timeoutMs` is configured longer than 300s, the default `Agent` kills the request on the headers wait before the SDK's own, longer timeout ever gets a chance to — a slow-but-healthy response is treated as failed.

---

## Decisions (and why)

| #   | Decision                                                                                                                                                                                                                                                                                                                                 | Rationale                                                                                                                                                                                                                                                                                              |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | The fix lives in the single shared `createProviderFromConfig()`, not a Digital-Ocean-specific code path. "Digital Ocean"/glm-5.3-flash is just a user-named **OpenAI-Compatible Provider** (`GLOSSARY.md`) entry — there is no vendor-specific code to patch.                                                                          | Patching one vendor's config entry fixes nothing the next time a different slow provider hits the same default.                                                                                                                                                                                      |
| D2  | Scope is the `headersTimeout` config fix only. No retry-on-timeout/backoff logic is added.                                                                                                                                                                                                                                              | Retries are a separate design (idempotency, backoff, double-billing on paid providers) deserving their own issue, not a rider here.                                                                                                                                                                  |
| D3  | `headersTimeout` is **derived** from a provider's own `timeoutMs`, not a new independently-configurable field.                                                                                                                                                                                                                          | See [ADR-0062](../../adr/0062-headers-timeout-derived-from-timeoutms-not-its-own-field.md).                                                                                                                                                                                                           |
| D4  | When `timeoutMs` **is** configured for a provider, construct an `undici.Agent({ headersTimeout: timeoutMs })` and attach it via `fetchOptions: { dispatcher: agent }` on the `configuration` object (OpenAI-family clients) or `clientOptions` object (Anthropic client) already built for that client. When `timeoutMs` is **not** configured, construction is byte-for-byte unchanged — no new default floor is invented.                                                                                                                                                                 | Matches the actual root cause (D-before-this-table) exactly; no behavior changes for providers that have never set `timeoutMs`.                                                                                                                                                                      |
| D5  | Applies to the `openai`, `azure-openai`, `anthropic`, and `openai-compatible` (both `authMode: 'oidc'` and `'apiKey'`) branches of `createProviderFromConfig` — i.e. every branch that already receives `timeoutMs` today. `ollama` is excluded; its `timeoutMs` gap is a separate, pre-existing, deliberately-deferred exclusion (comment at `provider-factory.ts:166-168`), not reopened by this work.                                                                                                                                                                                      | Fixing this bug is not the occasion to also solve Ollama's unrelated, already-documented gap.                                                                                                                                                                                                        |
| D6  | `bodyTimeout` (undici's other 300s default, same failure shape for a long streamed response body) is left untouched.                                                                                                                                                                                                                    | No evidence in the retrospective thread that `bodyTimeout` is firing; fixing an unreported problem is scope creep. A follow-up issue if it ever shows up.                                                                                                                                             |
| D7  | The `Agent({ headersTimeout })` construction is factored into one small shared helper reused across all five affected call sites in `provider-factory.ts`, rather than duplicated per branch.                                                                                                                                          | Root `AGENTS.md`'s "Composition over Customization" principle — one mechanism every relevant branch composes with, not five copies of the same four-line construction.                                                                                                                              |
| D8  | `undici` is added as an explicit direct dependency of `api/package.json` (today only transitive). The attach point (`fetchOptions.dispatcher`) was confirmed to type-check and run cleanly alongside the existing custom-`fetch` wrappers (`loggingFetch`, `createOidcAuthenticatingFetch`) against the installed SDK versions (`openai@6.45.0`, `@langchain/openai@1.6.2`, `@anthropic-ai/sdk@0.103.0`, `@langchain/anthropic@1.5.12`).                                                                                                                                                      | `node:undici` is not a public built-in module on Node 20/24 — the `Agent` class has to come from an installed `undici` package, and a version mismatch against whatever undici Node's own global `fetch` vendors internally is a documented failure mode (`UND_ERR_INVALID_ARG`) worth pinning carefully (see implementation note below). |
| D9  | No EDD eval scenario. This is a transport-layer config fix, not a change in model-facing behavior, so root `AGENTS.md`'s Evaluation-Driven Development rule doesn't apply. Coverage is a developer-level test extending the existing `describe('timeoutMs safety net', ...)` block in `api/src/services/provider-factory.test.ts`.    | Matches the precedent already in that test file for exactly this kind of per-provider-type construction assertion.                                                                                                                                                                                   |
| D10 | No `GLOSSARY.md` changes. `headersTimeout`/`timeoutMs`/the undici `Agent` are general programming concepts, excluded by `GLOSSARY-FORMAT.md`'s own inclusion rule even though the codebase uses them extensively; "Digital Ocean" is just an instance of the already-defined **OpenAI-Compatible Provider** term.                      | Keeps the glossary's own stated bar honest rather than force-fitting an entry because this issue happened to go through the domain-modeling process.                                                                                                                                                 |

---

## Non-goals

- Retry-on-timeout/backoff logic (D2) — separate issue if wanted.
- An independently-configurable `headersTimeoutMs` field or env var (D3, ADR-0062).
- Wiring `timeoutMs`/`headersTimeout` for `ollama` (D5) — pre-existing, separately-tracked gap.
- Any `bodyTimeout` change (D6).
- A new EDD eval scenario (D9).

---

## Open implementation notes (not design decisions — flagged for the implementer)

- Pin the `undici` dependency to a version compatible with whatever undici Node 24 (the Dockerfile's base image, `node:24`/`node:24-slim`) vendors internally for its global `fetch` — check this before picking a `package.json` version range, to avoid the dispatcher-incompatibility failure mode the `openai` SDK's own error message warns about (`UND_ERR_INVALID_ARG` / "invalid onRequestStart method").
- The shared helper (D7) is a few lines — colocate it in `provider-factory.ts` near the branches it serves rather than a new file.
- New tests (D9) should cover, per branch: `timeoutMs` set → dispatcher attached with a matching `headersTimeout`; `timeoutMs` unset → no dispatcher attached, construction unchanged — across all four in-scope branches (`openai`, `azure-openai`, `anthropic`, `openai-compatible` × both `authMode`s), following the existing per-provider-type assertion pattern already in `provider-factory.test.ts`.
- `docs/App-Docs/Providers.md`'s `timeoutMs` row (line 66) should get a short addendum noting it now also bounds `headersTimeout` when set, so the docs stay accurate.
