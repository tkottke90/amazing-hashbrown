# Webhook Task Creation — Design

Tracks: [tkottke90/amazing-hashbrown#252](https://github.com/tkottke90/amazing-hashbrown/issues/252), milestone v1.9.0

## Problem

External systems (CI pipelines, issue trackers, chatops, other automation)
have no way to create a new task in amazing-hashbrown without an
authenticated UI session hitting `POST /api/v1/tasks`. The only existing
webhook surface, `POST /api/v1/triggers/webhook/:token`
([#80](https://github.com/tkottke90/amazing-hashbrown/issues/80)), enqueues a
run of an **existing**, pre-configured task — it cannot create a new task,
and its only auth is an opaque token baked into the URL.

This adds a webhook endpoint that creates a new task, gated by an API key
accepted as a bearer token, plus API keys as a maintainable, first-class
concept (create, list, rotate, revoke) with a small UI under Settings.

## Scope decisions

These were made explicitly before implementation and should not be
revisited casually:

- **API keys are global** — not scoped to a workspace or user. Acceptable
  because the app is currently single-user; there is no cross-user access to
  protect against. Revisit if/when multi-user auth is added.
- **Auto-queueing is gated on workspace assignment.** A task created with a
  valid `x-workspace-id` can be auto-queued. A task created with no
  workspace lands in the Inbox and is **never** auto-queued, regardless of
  what the request payload asks for — it always waits for a user to review
  and queue it manually. This bounds the blast radius of a global API key.
- **`assignedTo` defaults to `'user'`** when the webhook payload omits it.
  This is a deliberate safe default: a caller must explicitly set
  `assignedTo: 'agent'` (together with `status: 'ready'` and a valid
  workspace) to get a task that runs automatically. Omitting it is a no-op
  from the scheduler's point of view — the task just sits for a human to
  pick up.
- **`status` in the webhook payload only ever accepts `'pending'` or
  `'ready'`.** Any other value is a `400`. Critically, `status: 'ready'`
  does **not** take effect unless `assignedTo` was *explicitly* `'agent'` in
  the same request — see "Status/assignedTo/workspace resolution" below.
  This preserves an existing invariant: nothing in this codebase has ever
  produced a task with `status: 'ready'` and `assignedTo !== 'agent'`
  (`board-rules.ts`'s `sourceOf()` and the R14 comment in
  `tasks.handlers.ts` both treat `'ready'` as shorthand for "there's a
  queued agent run"), and the webhook must not be the first thing that does.

## Data model

### New table: `api_keys`

Added via a new `ApiKeyStore` (own file, own migrations, same shared
`SqliteDatabase` instance as `WorkspaceStore`/`ThreadStore`/`WakeupStore` —
see "Store wiring" below).

```sql
CREATE TABLE api_keys (
  id          TEXT PRIMARY KEY,     -- randomUUID()
  name        TEXT NOT NULL,        -- user-given label, e.g. "Zapier"
  key_hash    TEXT NOT NULL UNIQUE, -- sha256(secret), hex-encoded
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL         -- bumped on rotate
);
```

The raw secret (`ahb_` + a `randomUUID()`-derived random string, following
the token-generation precedent set by #80) is returned exactly once, in the
response body of create and of rotate. It is never stored — only its SHA-256
hash is persisted, and the hash is never returned to a client. There is no
stored prefix or partial value for display; once shown, a key's value cannot
be recovered, only rotated (new secret, same row, same id, same name).

SHA-256 (not bcrypt/argon2) is the right tool here because the secret is
already high-entropy random data generated by the server, not a
human-chosen low-entropy password — there's nothing for a slow KDF to
protect against, and it would only add latency to every webhook call.

No `last_used_at` or usage tracking — not requested, and it would add a
write on every webhook call for no asked-for benefit. Can be added later if
wanted.

Revoking a key is a hard delete of its row, consistent with how this
codebase deletes other first-class rows (e.g. `deleteTaskHandler`) — no soft
delete, no audit trail, since none was requested.

### New column: `tasks.trigger_source`

```sql
ALTER TABLE tasks ADD COLUMN trigger_source TEXT NOT NULL DEFAULT 'user';
```

Records how a *task* was created (`'user'` or `'webhook'`). This is
intentionally a separate, narrower type from `task_queue.trigger_source`
(`TriggerSource = 'manual' | 'webhook' | 'schedule' | 'catch_up' | 'chat' |
'agent'`), which records what started a *run*. They share a column name and
a `'webhook'` value by coincidence of English, not by shared type — `tasks`
only ever needs `'user' | 'webhook'` today, and values like `'schedule'` or
`'catch_up'` don't mean anything for how a task was created.

**Explicitly not using the existing `tasks.origin` column** (`'user' |
'agent'`) for this. `origin` looks like generic metadata but is load-bearing
in the scheduler's dequeue logic (`origin='agent'` rows get special
single-flight/dispatch-group treatment in `WorkspaceStore`) — adding a third
value would risk silently changing that behavior for webhook-created tasks.
Webhook-created tasks keep `origin: 'user'`; `trigger_source` is the new,
narrowly-scoped field for creation provenance.

### Store wiring

`ApiKeyStore extends BaseStore` (the same base class `WorkspaceStore`,
`ThreadStore`, and `WakeupStore` extend), constructed with the one shared
`SqliteDatabase` instance. Follows the existing boot pattern exactly:

```ts
// api/src/services/api-key-store.ts
export function bootApiKeyStore(db: SqliteDatabase): void { ... }
export function getApiKeyStore(): ApiKeyStore { ... }
```

Wired into `api/src/index.ts` alongside the other `boot*Store(db)` calls.

## API surface

| File | Purpose |
|---|---|
| `api/src/services/api-key-store.ts` | `ApiKeyStore`: `create(name)`, `list()` (no hash/secret), `rotate(id)`, `revoke(id)`, `verify(secret)` (hash + lookup). |
| `api/src/middleware/api-key-auth.ts` | Express middleware: parses `Authorization: Bearer <key>`; `401` if missing, malformed, or unknown. Mounted only on the webhook route. |
| `api/src/routes/v1/api-keys.route.ts` + `api-keys.handlers.ts` | `POST /api/v1/api-keys` (create, `{ name }`), `GET /api/v1/api-keys` (list), `POST /api/v1/api-keys/:id/rotate`, `DELETE /api/v1/api-keys/:id` (revoke). Not bearer-gated — first-party UI endpoints, same trust level as every other route in this currently-unauthenticated app. |
| `api/src/routes/v1/webhooks.route.ts` + `webhooks.handlers.ts` | `POST /api/v1/webhooks/tasks`, gated by `api-key-auth` + a rate limiter. |

A distinct `webhooks.route.ts` (rather than extending `triggers.route.ts`)
keeps "create a task" cleanly separate from "run an existing task," and
avoids Express route-ordering foot-guns between a literal `/webhook/tasks`
path and the existing `/webhook/:token` param route.

### `POST /api/v1/webhooks/tasks`

```
Headers:
  Authorization: Bearer <key>     (required)
  x-workspace-id: <id>            (optional)
Body: same shape as POST /api/v1/tasks
  { title, description?, outcome?, assignedTo?, status?, dueAt?, ... }
```

**Status/assignedTo/workspace resolution** (the core logic of this
endpoint):

1. Validate `x-workspace-id` if present: `store.getWorkspace(id)` must
   return a workspace, else `400`. (Note: `createTask()`/`createTaskHandler`
   do **no** validation of `workspaceId` today — the UI only ever sends an
   id from its own dropdown. This validation is new, webhook-specific code.)
2. Validate `status` if present: must be `'pending'` or `'ready'`, else
   `400`.
3. Resolve `assignedTo`: whatever was sent, defaulting to `'user'` if
   omitted.
4. Create the task via `store.createTask()` — always lands at `'pending'`
   (that's all `createTask()` can do), with `trigger_source: 'webhook'`,
   `workspaceId` set to the validated workspace or `null`, `assignedTo` as
   resolved above.
5. **Only if** `workspaceId !== null` **and** `assignedTo === 'agent'`
   (explicitly, from the request) **and** `status === 'ready'` (explicitly,
   from the request): additionally call
   `store.patchTask(id, { status: 'ready' })` then
   `store.enqueueTask(id, { triggerSource: 'webhook' })` — mirroring the
   existing create→patch→enqueue shape in
   `WorkspaceStore.createTasks()` (used by the `create_tasks` chat tool).
6. In every other combination — no workspace, `assignedTo` is `'user'`
   (default or explicit), or `status` is `'pending'` — the task is left
   exactly as created. Requesting `status: 'ready'` without also explicitly
   requesting `assignedTo: 'agent'` does not partially apply; it is treated
   as `'pending'`.

There is no "already queued" check to add here: that guard
(`enqueueTaskHandler`'s `409`) protects against colliding with a run that
already exists for a given task id, which is structurally impossible for a
task this same request just created with a fresh id.

**Responses:**
- `201` — the created task, in the same boarded shape `POST /api/v1/tasks`
  returns.
- `400` — missing `title`, unknown `x-workspace-id`, or invalid `status`.
- `401` — missing/malformed/unknown API key. One generic message either way.
- `429` — rate limit exceeded.

### Rate limiting

`express-rate-limit` (already present transitively in the lockfile, not yet
a direct dependency or used anywhere) mounted only on
`POST /api/v1/webhooks/tasks`: 60 requests/minute per IP by default. Exists
because this endpoint may be exposed to the public internet, unlike the rest
of this app's currently-unauthenticated routes — it needs its own guard
against brute-force/DoS.

Threshold is configurable, not hardcoded: a new
`webhookRateLimitPerMinute` field on `AppConfigSchema` (default `60`), read
into `env`, per this repo's existing config convention
(`api/AGENTS.md`'s "Environment and config" section). The `429` response
body is normalized to this app's `{ error: string }` shape rather than
`express-rate-limit`'s default.

Scope is per-IP, not per-key — multiple keys behind the same NAT share one
budget. Accepted trade-off for this iteration (single-user app, likely a
handful of integrations); per-key limiting is unneeded complexity.

### `/api/v1/api-keys*`

```
POST   /api/v1/api-keys           { name } → 201 { id, name, key, createdAt }
GET    /api/v1/api-keys           → 200 [{ id, name, createdAt, updatedAt }]
POST   /api/v1/api-keys/:id/rotate → 200 { id, name, key, updatedAt }
DELETE /api/v1/api-keys/:id       → 204
```

`key` (the raw secret) appears only in the create and rotate responses,
never in list. `400` on missing/empty `name`; `404` on rotate/revoke of an
unknown id.

## UI

Folds into the existing Settings sub-nav pattern
(`ui/src/pages/settings/`) rather than becoming a new top-level tab/route —
reachable at `/settings?section=notifications`, exactly like every other
settings section:

| File | Change |
|---|---|
| `ui/src/pages/settings/settings-nav.tsx` | Add `'notifications'` to the `SettingsSlug` union and `{ label: 'Notifications', slug: 'notifications' }` to `NAV_ITEMS`. `VALID_SLUGS` picks it up automatically. |
| `ui/src/pages/settings/notifications-panel.tsx` (new) | One panel (no nested sub-nav — only one sub-section exists today), following the layout of `mcp-servers-panel.tsx`/`trackers-section.tsx`. Contains a "Webhooks" heading with: (1) the static endpoint URL, read-only + copy button, same pattern as `task-drawer.tsx`'s webhook-URL display; (2) a table of API keys (name, created date) with New / Rotate / Revoke actions. |
| `ui/src/pages/settings/index.tsx` | Add the `'notifications'` case to `ActivePanel`'s switch, import `NotificationsPanel`. |
| `ui/src/services/api-keys-api.ts` (new) | File-per-domain API client over the shared `request<T>()` wrapper, matching `tasks-api.ts`'s convention, for the four `api-keys` endpoints. |

**Reveal-once flow:** on create or rotate, the response's `key` is shown in
a one-time dialog (plain text, copy button, explicit "you won't see this
again" notice). No existing "reveal secret" component exists in this
codebase to reuse — this is new, but small, reusing the same copy-button
primitive already used for the webhook URL.

No new route, no new sidebar entry, no new top-level nav tab.

## Error handling

All new handlers use the existing `HandlerResult<T>` /
`ok()`/`badRequest()`/`notFound()`/`conflict()` convention from
`tasks.handlers.ts`/`triggers.handlers.ts` — no new response-shaping
pattern introduced.

See per-endpoint response tables above. The one cross-cutting rule: a
`401` from the webhook's auth middleware never distinguishes "key doesn't
exist" from "key is malformed" — a single generic message, to avoid leaking
which case applies.

## Testing

- `api-key-store.test.ts` **[unit]** — secret generated/hashed/returned
  once; `list()` never exposes the hash; `rotate()` overwrites the hash and
  returns a new secret; `revoke()` deletes the row; `verify()`
  matches/rejects correctly.
- `api-key-auth.middleware.test.ts` **[unit]** — missing header, malformed
  header, unknown key → `401`; valid key → calls `next()`.
- `webhooks.handlers.test.ts` **[unit/orchestration]** — the full
  status/assignedTo/workspace resolution matrix: default
  `assignedTo: 'user'`; invalid `status` rejected; unknown `workspace_id`
  rejected; `agent` + `ready` + valid workspace → patched to ready and
  enqueued; `ready` without explicit `assignedTo: 'agent'` → silently stays
  `pending`; **no workspace + `agent` + `ready` requested → still stays
  `pending`, never enqueued** (the core hardening rule from #252 — must not
  regress).
- `webhooks.route.test.ts` **[orchestration, supertest]** — full
  middleware → handler pipeline: `401` without auth, `429` over the limit,
  `201` happy path.
- `api-keys.route.test.ts` **[orchestration, supertest]** — create / list /
  rotate / revoke round trip over HTTP; asserts list responses never
  contain a secret or hash.
- UI (Jest): `notifications-panel.test.tsx` — URL copy button, key list
  render, reveal-once dialog on create/rotate, revoke confirmation flow.
  Update `settings-nav` test coverage for the new nav entry.
- **E2E (Playwright, required per this repo's UI-change policy):** a
  `@user-workflow` spec — Settings → Notifications, create a named key, see
  it revealed once, copy it, see it listed without the secret afterward,
  rotate it, revoke it. No LLM dependency, so it belongs in the CI-safe
  (`test:e2e:ci`) subset.
